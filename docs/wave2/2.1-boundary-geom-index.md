# Wave 2.1 — Fix indice spaziale GiST su `boundary_geom`

Data: 2026-05-29
Audit ref: Wave 2 full-audit, dimensione "Database, models & migrations",
finding HIGH #5 ("boundary_geom GiST index is silently never created") +
#6 ("spatial query paths untested"). Verificato in produzione.

## Problema (causa-radice)

Collisione di **nome** tra due migration:

| Migration | Nome indice | Definizione | Stato prod |
|---|---|---|---|
| `004_postgis_indexes` | `ix_geo_entities_boundary_geom` | `GIST(ST_GeomFromGeoJSON(boundary_geojson))` — **expression** | ✅ esiste, usato |
| `019_boundary_geom_postgis` | `ix_geo_entities_boundary_geom` (stesso nome) | `GIST(boundary_geom)` — **colonna** | ❌ no-op silenzioso |

`019` usa `CREATE INDEX IF NOT EXISTS <nome>`: poiché `004` gira prima e il nome
è già occupato, PostgreSQL salta la creazione (NOTICE, non errore). L'indice sulla
**colonna** `boundary_geom` non è mai stato creato.

### Verifica produzione (2026-05-29)

```
ix_geo_entities_boundary_geom      → GIST (st_geomfromgeojson(boundary_geojson))   [004, expression]
ix_geo_entities_boundary_geom_temp → GIST (st_geomfromgeojson(boundary_geojson))   [duplicato, residuo one-off]
(nessun indice GiST sulla colonna boundary_geom)
```

### Impatto

`src/api/routes/_entities_helpers.py`:
- `_apply_bbox_filter` → `ST_Intersects(boundary_geom, envelope)` (riga ~320)
- `_apply_contains_filter` → `ST_Contains(boundary_geom, point)` (riga ~387)

Entrambi filtrano sulla **colonna** `boundary_geom`, che è priva di indice → girano
in **sequential scan con valutazione geometrica per-riga** sull'endpoint primario
`/v1/entities` (parametri `?bbox=` e `?contains=`). È esattamente l'O(n) che ADR-009
/ migration 019 volevano eliminare (target p95 < 50 ms). A ~1038 entità l'impatto
in ms assoluti è oggi tollerabile, ma il meccanismo è rotto ed è sensibile al volume.

L'expression index `004` **non** è utilizzabile per un predicato sulla colonna:
serve solo a `_where_was_postgis` (che filtra su `ST_Contains(ST_GeomFromGeoJSON(boundary_geojson), …)`).

## Fix (migration 022)

1. **Crea** `ix_geo_entities_boundary_geom_gist` = `GIST(boundary_geom)` (nome distinto).
2. **Droppa** `ix_geo_entities_boundary_geom_temp` (duplicato ridondante dell'expression
   index, residuo di `scripts/sites_fk_backfill_v2.sql`, mai referenziato in query).
3. **Lascia intatto** `ix_geo_entities_boundary_geom` (004, expression) — usato da `_where_was_postgis`.
4. Corregge il docstring fuorviante in `_entities_helpers.py` (citava l'indice sbagliato).

Solo PostgreSQL; SQLite (dev/test) → no-op. Idempotente (`IF NOT EXISTS` / `IF EXISTS`).
`CREATE INDEX` non-`CONCURRENTLY` perché gira nella transazione Alembic e su ~1038
righe il build è sub-secondo (lock trascurabile).

## Verifica post-deploy (smoke)

```sql
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename='geo_entities' AND indexdef ILIKE '%gist%';
-- atteso: ix_geo_entities_boundary_geom (expression) + ix_geo_entities_boundary_geom_gist (colonna)
-- NON atteso: ix_geo_entities_boundary_geom_temp
```

```sql
EXPLAIN ANALYZE
SELECT id FROM geo_entities
WHERE boundary_geom IS NOT NULL
  AND ST_Intersects(boundary_geom, ST_MakeEnvelope(-10,35,30,60,4326));
-- atteso: Index Scan using ix_geo_entities_boundary_geom_gist (non Seq Scan)
```

## Stop condition

Migration Alembic **nuova** → richiede OK esplicito di Clirim prima del deploy.
Additiva e reversibile (no perdita dati): `CREATE INDEX` + `DROP INDEX` di un duplicato.
